Phase 0: Infrastructural Agents and Hardware Calibration Based on the "Draft BuildOrder," the "Implementation Roadmap," and the hardware specifications provided in your documentation (Ryzen 7 8700F, RTX 4060, 32GB RAM), Phase 0 is indeed the critical moment to architect around hardware constraints. While this phase is primarily about establishing the "laws of physics" for the system, it must be engineered to fit within the physical reality of your compute resources. Here is the detailed analysis of hardware considerations and the specific "Infrastructural Agents" that exist in Phase 0.

Hardware Constraints & Architectural Calibration (Phase 0) Objective: You are designing a system intended to scale to 40–50 specialized agents [1]. Your current hardware (RTX 4060 with 8GB VRAM, 32GB System RAM) [2] imposes hard physical limits that Phase 0 must address through efficient architectural choices. You cannot run 50 concurrent Large Language Models (LLMs) on this hardware; therefore, Phase 0 must codify serialization and resource efficiency into the communication protocols. • Constraint 1: VRAM Bottleneck (The 8GB Limit) ◦ Impact: A standard 7B parameter model (like Mistral or Llama 3) requires approx. 14GB VRAM at fp16, or ~5-6GB quantized to 4-bit. Your RTX 4060 can barely hold one active reasoning agent at a time. ◦ Phase 0 Mandate: You must implement a Stateful Serialization Protocol within the Agent Management System (AMS). The AMS cannot allow agents to run in parallel (asynchronous concurrency) regarding VRAM usage. It must implement a "context-switching" architecture where agent weights are swapped in/out, or more likely, agents act as lightweight "prompts" routed to a single, central LLM backend service (acting as the shared brain) rather than 50 separate loaded models. ◦ Storage Consequence: The Vector Database (Action 3.2) [3] serves as the "Long-Term Memory." With 32GB system RAM, you must select a lightweight vector store (e.g., Milvus or Chroma running in persistent mode rather than in-memory) to reserve RAM for the active model context window. • Constraint 2: Context Window & Token Economy ◦ Impact: Passing full conversation histories between agents bloats the context window, slowing generation and causing "out of memory" (OOM) crashes. ◦ Phase 0 Mandate: The FIPA-ACL implementation [4] must strictly enforce Conversation ID tracking and Context Extraction. You cannot pass raw text history. Agents must pass compressed OMDoc objects [5]. Phase 0 must define the schema for "state passing" so that an agent receives only the mathematical state (the current equation) and not the conversational fluff, maximizing the efficiency of your 32GB RAM.



The "Silent" Agents of Phase 0 Query: Is there agents in phase 0? Answer: Yes. While there are no cognitive agents (no "Thinkers" or "Solvers" like the Algebra Supervisor), Phase 0 requires the instantiation of Infrastructural Agents. These are "Bureaucratic Agents" that manage the existence and discovery of the future workforce. They are "silent" because they produce no math, but they are active code entities. • Agent 1: The Agent Management System (AMS) ◦ Type: Simple Reflex Agent [6]. ◦ Role: The "God Agent" or "Lifecycle Manager." ◦ Function: It maintains the "White Pages" of the system. In Phase 0, you build this agent to handle the create_agent, kill_agent, and suspend_agent commands. On your hardware, the AMS is the critical gatekeeper that enforces the "One-Model-At-A-Time" rule to prevent VRAM overflow. It holds the ultimate authority to grant or deny an agent's request to spin up [7, 8]. ◦ Hardware Relevance: It monitors system resources (RAM/VRAM usage) and rejects new agent instantiation requests if the threshold (e.g., 90% memory usage) is breached. • Agent 2: The Directory Facilitator (DF) ◦ Type: Model-Based Reflex Agent [6]. ◦ Role: The "Yellow Pages" or "Service Registry." ◦ Function: It creates a dynamic lookup table. Future agents (like the Calculus Supervisor) will register their services here (e.g., service: integration, cost: high). In Phase 0, you build the DF to accept these registrations and respond to queries. It allows the Orchestrator to say "Find me an integration agent" without knowing who or where that agent is [7, 8]. • Agent 3: The Agent Communication Channel (ACC) ◦ Type: Transport Layer / Routing Agent [8]. ◦ Role: The "Postmaster." ◦ Function: It is responsible for the actual routing of FIPA-ACL messages [9]. It ensures that a message sent from Agent A actually reaches Agent B. In Phase 0, you configure the ACC to handle the OMDoc payloads and ensure that messages are queued if the receiving agent is currently "swapped out" to save VRAM.
