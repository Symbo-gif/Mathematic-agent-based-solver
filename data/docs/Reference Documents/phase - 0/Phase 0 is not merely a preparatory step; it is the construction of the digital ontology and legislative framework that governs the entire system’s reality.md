Phase 0 is not merely a preparatory step; it is the construction of the digital ontology and legislative framework that governs the entire system’s reality. Before a single problem-solving agent (like the Orchestrator) is instantiated, the "physics" of their interaction—how they speak, how they remember, and how they discover one another—must be codified.
Failure to execute Phase 0 with extreme rigor results in a "Tower of Babel" scenario where highly capable agents exist in isolation, unable to transmit the semantic nuance of mathematical concepts, rendering the collective intelligence inert [1], [2].
Here is the expanded, step-by-step technical specification for Phase 0: The Linguistic & Infrastructural Bedrock.
- 
Step 1: Architecting the Semantic Substrate (The "Lingua Franca")
Objective: Eliminate natural language ambiguity by enforcing a rigorous mathematical data standard. Raw text or LaTeX is forbidden for inter-agent logic because it conveys presentation (how it looks) rather than content (what it means).
- Action 1.1: Implement OMDoc/OpenMath Standards
    ◦ Directive: You must adopt the OMDoc (Open Mathematical Documents) or OpenMath standard as the mandatory exchange format. This ensures that a "derivative" is understood as a mathematical operator, not just a text string [2], [3].
    ◦ Implementation Detail: Construct the data schema to support three specific layers of abstraction mandated by the architecture: 1. Object Level: Encodes formulae (e.g., specific variables and operations like x

 +y). 2. Statement Level: Encodes definitions, theorems, and proofs as distinct logical entities. 3. Theory Level: Encodes the modular mathematical theories (e.g., "Group Theory") that provide context for the statements [4], [5].
- Action 1.2: The Translation Layer
    ◦ Directive: Build the translation interfaces now. While agents reason in OMDoc, the system must ingest natural language and output human-readable math.
    ◦ Mechanism: Establish the specifications for the Autoformalization Pipeline (to be populated by the Analysis Team in Phase 1) which will eventually translate user text into this formal semantic structure, ensuring downstream agents never encounter ambiguous natural language [6], [7].
- 
Step 2: Establishing the Constitutional Law (FIPA-ACL Protocols)
Objective: Replace ad-hoc messaging with a deterministic legal framework for agent interaction. The system cannot rely on agents "chatting"; they must issue binding commands and binding acceptances.
- Action 2.1: Implement FIPA-ACL (Agent Communication Language)
    ◦ Directive: Adopt the FIPA Abstract Architecture. Every message passed between agents must be a structured FIPA-ACL packet containing specific key-value pairs: performative (the type of act), sender, receiver, content (the OMDoc payload), ontology (the domain context), and protocol [8], [9].
    ◦ Crucial Constraint: Strict adherence to Speech Act Theory is required. A message is not just information; it is an action. Defining the performative (e.g., REQUEST, INFORM, REFUSE) eliminates ambiguity regarding the sender's intent [9], [10].
- Action 2.2: The Conversation Management System
    ◦ Directive: Implement mandatory Conversation IDs in the message header.
    ◦ Reasoning: Mathematical problem solving is asynchronous and non-linear. When an Integration Specialist returns a result, it must reference the specific conversation-id of the original request. This prevents "context loss" and token overhead by allowing agents to track thread-specific states without re-reading the entire system history [9].
- 
Step 3: The Active Memory Architecture (The Blackboard)
Objective: Move beyond stateless interactions. Construct a dynamic, centralized memory systems that allows for "Write-Once, Read-Many" collaboration.
- Action 3.1: The Shared Blackboard
    ◦ Directive: Deploy a centralized Blackboard Architecture. This is the common workspace where agents post partial results, lemmas, and failed attempts.
    ◦ Mechanism: It must be more than a log; it requires a Publish-Subscribe mechanism (via FIPA-Subscribe). For example, the Geometry Agent should be able to "subscribe" to updates regarding "Variable x", instantly receiving a notification when the Algebra Agent solves for x. This decouples the agents, allowing for emergent parallel problem solving [11], [12], [13].
- Action 3.2: The Vector Database Backbone
    ◦ Directive: Initialize a vector database (e.g., Milvus, Pinecone, or Weaviate) to serve as the long-term memory substrate.
    ◦ Purpose: This infrastructure is the prerequisite for Retrieval-Augmented Generation (RAG). Even before the "Knowledge Management Team" (Phase 3) is hired, the storage architecture must be built to index mathematical "thought traces" and theorem embeddings, enabling the system to eventually recognize recurring problem patterns [14], [15].
- 
Step 4: The Registry & Discovery Services (The "Yellow Pages")
Objective: Enable dynamic discovery. Agents should not have hard-coded IP addresses for one another; they must look up capabilities dynamically.
- Action 4.1: The Agent Management System (AMS)
    ◦ Directive: Build the AMS, the "God Agent" responsible for the lifecycle of all other agents. It handles creation, deletion, and authentication. It ensures that every agent has a unique, native identity (akin to an IAM principal), enforcing least-privilege access and security boundaries from the very start [16], [17].
- Action 4.2: The Directory Facilitator (DF)
    ◦ Directive: Implement the Directory Facilitator to act as the "Yellow Pages."
    ◦ Logic: When the Orchestrator needs to "integrate a function," it queries the DF for agents that have registered the service service: symbolic-integration. This decouples the architecture; you can add five new integration specialists later, and the Orchestrator will find them automatically without code changes [16], [18].
- 
Step 5: The Agent Cognitive Template (BDI Logic)
Objective: Define the internal operating system for the individual agents. They cannot be simple scripts; they must be deliberative entities.
- Action 5.1: The Belief-Desire-Intention (BDI) Framework
    ◦ Directive: Code the standard BDI Control Loop template that all future agents (Phase 1-4) will inherit.
    ◦ The Loop Structure: 1. Beliefs (B): The agent's current knowledge (e.g., "I know the value of x"). 2. Desires (D): The agent's goal (e.g., "I want to solve this integral"). 3. Intentions (I): The committed plan (e.g., "I will apply the Risch Algorithm").
    ◦ Significance: This separates deliberation (choosing a plan) from execution (doing the math), which is critical for handling the complexity of high-level mathematical reasoning [19], [20].

Phase 0 Deliverable: The "Silent" System
At the conclusion of Phase 0, you possess a system that can do no math, yet contains the entire potential of the project. You have a Blackboard waiting for data, a DF waiting for registrations, a FIPA legal code waiting to adjudicate disputes, and an OMDoc lexicon waiting to be spoken. Only upon this immutable bedrock can you safely instantiate the Tier 1 Orchestrator in Phase 1.
