# Phase 1 Coding Strategy: Architecting the Cognitive Chassis

## 1.0 The Strategic Mandate: Building a Verifiable Reasoning Core

Phase 1 marks the transition from the static, foundational infrastructure of Phase 0 to the first dynamic "heartbeat" of the system. The primary objective of this phase is not to achieve broad mathematical capability, but to construct a reliable, hallucination-resistant reasoning core. This is the foundational Cognitive Chassis upon which all future intelligence will be built.

The central architectural mission of Phase 1 is to solve the fundamental reliability crisis in AI: standard systems generate "plausible but incorrect answers." Our mandate is to "Shackle Neural Creativity to Symbolic Rigor." In practice, this principle means that every creative or intuitive step generated by any component must be validated by a deterministic, symbolic system before it can be accepted as truth.

To enforce this, Phase 1 establishes the core operational pattern of the entire system: the Orchestrator-Prover-Verifier loop. This feedback mechanism is the fundamental engine that guarantees the system can legally and verifiably solve a problem without hallucinating. Before constructing the new agent teams that form this loop, it is essential to understand how they will leverage the civic infrastructure already established in Phase 0.

## 2.0 Foundational Dependencies: Leveraging Phase 0 Infrastructure

The new cognitive agents of Phase 1 do not operate in a vacuum. They are citizens of a digital society whose laws and infrastructure were codified in the previous development phase. Their success is entirely dependent on their ability to integrate with and adhere to this pre-existing foundation.

## 3.0 Implementation Blueprint: The Cognitive Agent Teams

This section details the core technical specification for Phase 1. The system's "Cognitive Chassis" will be constructed by implementing four distinct, specialized agent teams, each with a precise function in the reasoning pipeline.

## 3.1 Step 1: The Gatekeepers (Problem Analysis Team)

The objective of this team is to act as the system's primary interface, sanitizing chaotic natural language and LaTeX inputs into structured, unambiguous mathematical objects. This critical first step prevents the "Garbage In, Garbage Out" failure mode by ensuring only clean, well-formed data enters the reasoning core.

Syntax Parser & Autoformalizer: This agent functions as the system's "transducer." Its directive is to translate raw text and LaTeX into structured OMDoc/OpenMath expression trees. For example, it converts the string "Find the derivative of x squared" into a formal OpenMath object that downstream agents can process mathematically.
Structure Recognizer: This agent acts as a meta-classifier. Its function is not to solve but to categorize the incoming structured problem. It tags each problem by type—such as Computation, Proof, or Optimization—and appends this tag to the problem's metadata for use in the Orchestrator's downstream routing logic.

## 3.2 Step 2: The Central Nervous System (Main Orchestrator)

The Orchestrator's objective is to serve as the system's Tier 1 "General Contractor." Its core mandate is to manage the problem-solving process while enforcing the strict architectural separation of Problem Understanding from Problem Solving.

Decomposition Engine: The Orchestrator is programmed with Hierarchical Task Network (HTN) logic, enabling it to break complex requests into a sequence of smaller sub-goals (e.g., "First simplify, then integrate").
Dynamic Routing Logic: The Orchestrator connects to the Phase 0 Directory Facilitator (DF) to discover available agents. When it receives a problem tagged "Calculus," it queries the DF to find an agent registered with that capability and assigns the task accordingly.
The "Non-Intervention" Directive: A critical, hard-coded constraint is that the Orchestrator is strictly forbidden from performing calculations itself. If it sees '2+2', it must delegate, never compute. This enforces the architectural discipline required for future scaling.

## 3.3 Step 3: The Pilot Solver (The Symbolic Wrapper)

The strategic purpose of this agent is to serve as a temporary "stand-in" for the future, more complex agent workforce. It acts as a "tracer bullet" to verify that the end-to-end data pipeline—from user input to final output—is fully functional before adding further complexity.

This agent encapsulates the robust SymPy Computer Algebra System (CAS) within a standard agent shell. It functions as the "Prover" or "Executor" in the reasoning loop. Its role is to subscribe to OMDoc-formatted tasks posted on the Blackboard, execute deterministic symbolic operations (like sympy.diff), and post the resulting candidate answer back to the Blackboard.

## 3.4 Step 4: The Immune System (Verification Core)

The critical objective of this team is to implement the Ax-Prover pattern as the system's primary defense against hallucination. No result from any solver is permitted to be presented to the user until it has been stamped "Approved" by this core verification team.

This team provides a two-layered defense mechanism:

First Line of Defense: The Logic Checker: This is a rule-based agent that inspects the logical flow of a proposed solution. It scans for common "illegal moves" or unstated assumptions, such as dividing by a variable without first confirming it is non-zero, to address the "Assumption Gap."
Second Line of Defense: The Formal Verifier Wrapper: This agent wraps a formal theorem prover, such as Lean 4, Coq, or Isabelle. It treats the output from the Pilot Solver as a "candidate proof" and attempts to formally compile it. This serves as the final, absolute check against hallucination; if a solution can be formally proven, it is correct.

## 3.5 The Neural-Symbolic Verification Loop

The Verification Core manages a strict success/failure feedback loop that is fundamental to the system's reliability.

The Verification Core intercepts a candidate proof: It retrieves a solution posted by the Pilot Solver on the Blackboard.
Compilation Attempt: The Formal Verifier agent attempts to compile the candidate proof within its formal system.
Success Path: If the proof compiles successfully, the agent marks the result with STATUS: VERIFIED on the Blackboard. The Orchestrator is then permitted to retrieve the answer and release it to the user.
Failure Path: If the proof fails to compile, the agent raises an ERROR FLAG on the Blackboard. This flag is a feedback signal that instructs the Orchestrator to retry the task, potentially delegating it to a different solver or using an alternative strategy.

The successful implementation of these components and their interactions culminates in the system's first integrated test.

## 4.0 Integration & Validation: The "First Breath" End-to-End Test

The purpose of this final step is to run the first live, end-to-end test to validate that the entire Cognitive Chassis functions as a single, cohesive unit. This test serves as the "first breath" of the integrated system.

The official test case is: "Calculate the derivative of x² + 1."

The journey of this query through the system validates the complete architecture:

The Gatekeepers: The Problem Analysis Team receives the raw text. The Syntax Parser converts it into a structured OMDoc object, and the Structure Recognizer tags it as Calculus/Computation.
The Orchestrator: The Main Orchestrator receives the structured problem and its tag from the Gatekeepers. It queries the Directory Facilitator for a "Calculus" service, discovers the Pilot Solver, and posts the formal OMDoc task to the Blackboard.
The Pilot Solver: The SymPy Wrapper agent, subscribed to calculus tasks, retrieves the task from the Blackboard. It executes the command sympy.diff(x**2 + 1) and posts the candidate result, 2*x, back to the Blackboard.
The Immune System: The Verification Core intercepts the candidate result. The Logic Checker inspects the steps and finds no illegal moves. The Formal Verifier Wrapper then successfully compiles the formal proof for this derivative. The result is marked STATUS: VERIFIED.
Final Output: The Orchestrator observes the STATUS: VERIFIED status on the Blackboard, retrieves the verified result, and presents the final, trusted answer: "The answer is 2x."

This successful test run signifies the completion of the Phase 1 build and establishes the final deliverable.

## 5.0 Phase 1 Deliverable: Architecturally Complete, Mathematically Limited

At the conclusion of Phase 1, the system is fully operational. It is architecturally complete, with a functional and verified reasoning loop, but remains mathematically limited, as its capabilities are bound to the SymPy library. This outcome is not a shortcoming but the intended design, prioritizing the perfection of the chassis before installing more powerful engines.

Two critical separations of concern have now been successfully hard-coded into the system's architecture:

Separation of Planning from Execution: The Orchestrator is responsible for planning, decomposition, and delegation, while the Pilot Solver is responsible for execution. The Orchestrator manages; it never solves.
Separation of Intuition from Verification: The Pilot Solver provides a candidate answer (the "intuition"), while the Verification Core is responsible for proving that the answer is correct and free of logical flaws. The system never trusts; it always verifies.

The Road to Phase 2

With the verifiable chassis and the essential feedback loop now in place, the foundation is set. The Cognitive Chassis is not just a demo; it's a scalable framework designed for expansion. The next step in Phase 2 is to replace the single "Pilot Solver" with a massive, specialized workforce of Tier 2 agents. With the chassis built and the verification loop in place, the system is now ready to safely and reliably scale its mathematical capabilities.
