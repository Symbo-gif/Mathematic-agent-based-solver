## Phase 3 is designated as the Meta-Cognitive Middleware implementation. While Phase 2 populated the system with "Muscle" (mathematical solvers), Phase 3 installs the "Conscience" and "Memory." Without these agents, the Phase 2 workforce is brittle: it will confidently compute results for impossible problems (hallucination) and waste resources re-solving known lemmas (amnesia). Phase 3 introduces three critical cross-cutting teams to address the Assumption Gap, the Memory Gap, and the Search Gap [1], [2], [3]. Here is the detailed technical specification for the agent teams required in Phase 3.
The Precondition Validation Team (The "Anesthesiologist") Objective: Address the Assumption Gap (Gap 3). This team acts as a mandatory "Pre-Flight Checklist" before any solver is allowed to touch a problem. Its sole purpose is to prevent the system from "hallucinating" answers to mathematically invalid queries (e.g., finding real roots for x 2 +1=0) [4], [5]. • Agent 1.1: The Domain Checker ◦ Directive: This agent audits the problem against the capabilities of the available solvers. It functions as a solvability gatekeeper. ◦ Logic: It verifies if the problem falls within a decidable fragment of mathematics. If the input requires solving a Diophantine equation (undecidable in general) and the system only possesses Real arithmetic solvers, this agent halts execution immediately with a DOMAIN_MISMATCH error, preventing infinite loops or wasted compute [5], [6]. • Agent 1.2: The Assumption Validator ◦ Directive: A rigorous compliance agent that scans the OMDoc/OpenMath structure for variable definitions and constraints. ◦ Mechanism: It enforces mathematical legality. For example, if the problem contains ln(x), this agent asserts the constraint $x > 0$. If a prior step or user input defined x=−5, the Validator triggers a CONSTRAINT_VIOLATION error before the Logarithm Specialist is ever invoked. This prevents the generation of "correct" calculations based on impossible premises [4], [5]. • Agent 1.3: The Edge Case Detector (Red Team) ◦ Directive: A proactive "saboteur" agent that hunts for singularities and boundary failures. ◦ Task: It interrogates the problem state with "What if?" scenarios. "What breaks if the denominator is zero?" or "Is this matrix singular?" If the Linear Algebra Supervisor attempts to invert a matrix, this agent first calculates the determinant. If det(A)=0, it blocks the operation, saving the system from a computational crash [5], [6]. • Agent 1.4: The Constraint Propagator ◦ Directive: This agent ensures that the "laws of physics" established for the problem are respected by all downstream agents. ◦ Function: If the Orchestrator determines n must be an integer, the Constraint Propagator injects this constraint into the context of every sub-task. This ensures the Integration Expert does not attempt algorithms valid only for continuous real variables on a discrete variable [5], [6].



The Knowledge Management Team (The "Librarians") Objective: Address the Memory Gap (Gap 2). This team transforms the system from a stateless processor into a learning engine. It ensures that insights discovered by one agent are instantly available to all others, preventing redundant computation [4], [7]. • Agent 2.1: The Context Extractor ◦ Directive: An information filter that sits between the User/Orchestrator and the Blackboard. ◦ Function: It parses the full problem history to extract only the signal relevant to the current sub-task. By filtering out noise, it ensures the solvers operate on a clean, token-efficient context, preventing "distraction" by irrelevant data [7], [8]. • Agent 2.2: The Memory Indexer ◦ Directive: The archivist for the system, responsible for writing to the Vector Database (Long-Term Memory). ◦ Mechanism: When a Supervisor confirms a result (e.g., "Equation 1 simplifies to x+1"), the Memory Indexer embeds this result and stores it. This creates a persistent record that survives beyond the current execution cycle, allowing the system to recall this lemma in future problems [7], [8]. • Agent 2.3: The Retrieval Specialist (RAG Integration) ◦ Directive: An external liaison agent responsible for querying vast mathematical repositories. ◦ Capability: It connects to formal libraries like Mathlib, Loogle, or internal historical logs. Before a solver attempts a proof, this agent queries: "Do we already have a theorem for this?" If a match is found, it retrieves the theorem, effectively short-circuiting the solving process. Research indicates this Retrieval-Augmented Generation (RAG) approach improves accuracy by ~15-20% [4], [7].



The Hypothesis Generation Team (The "Scouts") Objective: Address the Search Gap (Gap 1). Standard agents are linear; they blindly follow the first path they see. This team enforces Tree-of-Thoughts (ToT) reasoning, exploring the "solution space" to find the optimal path before committing resources [4], [9]. • Agent 3.1: The Hypothesis Generator ◦ Directive: A creative agent strictly forbidden from solving. Its job is to propose strategies. ◦ Output: It generates high-level plans. For a complex proof, it might output: 1. "Plan A: Attempt Proof by Induction." 2. "Plan B: Attempt Proof by Contradiction." 3. "Plan C: Direct Algebraic Manipulation." [9], [10]. • Agent 3.2: The Path Evaluator ◦ Directive: A heuristic judge that estimates the "Promise Score" of the proposed plans. ◦ Logic: It analyzes the problem structure to predict success. "This problem has a recursive structure, so 'Induction' has a 90% promise score; 'Contradiction' has 20%." The system then executes the highest-scoring plan first, avoiding dead ends [9], [10]. • Agent 3.3: The Backtracking Manager ◦ Directive: The state-management agent responsible for "Time Travel." ◦ Mechanism: If Plan A fails (hits a dead end), this agent resets the Blackboard state to the "pre-solving" snapshot and triggers Plan B. This allows the system to recover gracefully from failed hypotheses rather than crashing [9], [10].



Wiring the "Meta-Brain" (Orchestrator Update) Objective: In Phase 3, the Tier 1 Orchestrator (built in Phase 1) must be updated to utilize these new teams. The control loop shifts from a simple Plan -> Solve to a robust Analyze -> Hypothesize -> Validate -> Solve cycle [11]. • Protocol 1: The "Pre-Flight" Check ◦ Constraint: The Orchestrator is now hard-coded to never delegate a task to a Tier 2 Domain Supervisor until the Precondition Validation Team returns a STATUS: VALID token. • Protocol 2: The "Look-Before-You-Leap" Check ◦ Constraint: Immediately after classification, the Orchestrator must query the Knowledge Management Team. If the Retrieval Specialist finds a high-confidence match (e.g., "This is a known identity"), the solving phase is skipped entirely. • Protocol 3: The "Scouting" Check ◦ Constraint: For problems tagged "High Complexity," the Orchestrator must invoke the Hypothesis Generator first. It then delegates the selected strategy (e.g., "Use Induction") to the Domain Supervisors, rather than just the raw problem [11]. Phase 3 Deliverable: The "Resilient" System At the conclusion of Phase 3, the system has transformed from a "Fragile Genius" into a Resilient Professional. • Behavior: If asked to "Calculate the real square root of -4," the Phase 2 system would hallucinate. The Phase 3 system's Assumption Validator catches the domain constraint violation and politely refuses: "Error: Real domain constraint violated." • Efficiency: If asked a complex combinatorics question, the Hypothesis Generator evaluates paths, and the Retrieval Specialist might find a solved identity in Mathlib, answering in milliseconds rather than minutes of calculation [12].
