Strix Application Security Testing Orchestration
Strix provides a unified framework for automating AI-powered application security testing. It simulates hacker behavior using autonomous AI agents to identify and validate vulnerabilities within various target types, including local codebases, GitHub repositories, and deployed web applications. This is achieved through a core orchestration system that manages agent behavior, facilitates interactions with Large Language Models (LLMs), executes security tools within isolated environments, and collects comprehensive telemetry for reporting and proof-of-concept generation.

The entire system resides within the (root) directory, which encompasses the agent's core logic, LLM integration, runtime environment management, and telemetry services. Its design aims to reduce false positives associated with static analysis and the manual overhead of traditional penetration testing by dynamically analyzing applications and validating findings. For details on setting up the development environment and contributing, refer to Strix Core Framework: Setup and Contribution.

At the heart of Strix are its AI agents, which are responsible for performing security scans. These agents operate autonomously, managing their own state, interacting with LLMs to interpret instructions and formulate actions, and executing a diverse set of sandboxed tools. The agent's lifecycle, from initiation to completion, is carefully managed, including handling environment validation, Docker image management, and argument parsing, which dispatches operations to either command-line or interactive text-based interfaces. For a deeper understanding of agent mechanics, see Agent Operations and Lifecycle Management.

The agents' intelligence is powered by their integration with LLMs. Strix provides a unified interface for LLM interactions, handling configuration, robust request management, and memory compression to manage conversational context effectively. This includes parsing LLM outputs to extract tool invocations and managing various agent prompt modules that imbue agents with specialized knowledge across different security domains. More information on this integration can be found under Large Language Model (LLM) Integration.

To ensure secure and controlled execution, Strix leverages isolated sandboxed environments for its tools. This involves provisioning and destroying Docker containers, within which a FastAPI server securely executes various security tools. This isolation is critical for preventing tools from affecting the host system and for managing dependencies. The underlying mechanisms are detailed in Runtime Environment and Sandboxed Tool Execution.

A rich set of tools and capabilities is available to the Strix agents, enabling them to perform complex security assessments. These tools cover areas such as browser automation, file system interaction, Python code execution, proxy manipulation for traffic analysis, note-taking, web search, terminal command execution, and structured vulnerability reporting. The framework supports both local and sandboxed execution of these tools, with a registry for discoverability and execution management. Strix Tools and Capabilities elaborates on these.

Throughout the scan process, Strix meticulously collects telemetry data. This global tracing mechanism records all agent activities, tool executions, chat messages, and vulnerability reports. This data is then persisted to a dedicated run directory, forming the basis for auditing scans, understanding agent behavior, and generating comprehensive vulnerability reports, often with proof-of-concepts. For further details, refer to Telemetry and Vulnerability Reporting.

Agent Operations and Lifecycle Management
The Strix Application Security Testing Orchestration system relies on cybersecurity agents that operate autonomously to perform security scans. These agents manage their operational state, interact with large language models (LLMs) to inform their decisions, execute various tools within sandboxed environments, and communicate with other agents. The framework supports flexible scan targets and provides clear entry points for controlling an agent's lifecycle, from initial environment setup to real-time status updates via command-line or text-based interfaces.

The orchestration of an agent's activities is primarily managed by the BaseAgent class in strix/agents/base_agent.py. This class provides the foundational asynchronous execution loop, which handles LLM interactions, processes tool invocations, and manages various execution conditions such as cancellations and errors. The BaseAgent also integrates with a global tracing mechanism for comprehensive logging and monitoring of agent activities and status changes. This is critical for observability in complex multi-agent systems and is central to the overall Telemetry and Vulnerability Reporting system.

The operational status of an agent is tracked using the AgentState class, defined in strix/agents/state.py. This data model encapsulates information such as the agent's ID, its assigned task, conversation history, actions taken, and flags indicating its lifecycle status, including iteration limits, waiting states, and error conditions. Explicit methods are provided to manage state transitions, ensuring data consistency throughout the agent's operation. For example, set_completed marks an agent's task as finished, while enter_waiting_state places the agent in a pause state, awaiting further input or conditions.

For security-specific tasks, the StrixAgent class, an extension of BaseAgent, is responsible for orchestrating scans. The execute_scan method within strix/agents/StrixAgent/strix_agent.py processes diverse scan target types, such as code repositories, local files, URLs, and IP addresses. It transforms these targets into a structured task description that guides the agent's main execution loop. This allows for adaptability in defining and launching security assessments.

The Strix system provides two primary interfaces for managing and monitoring agent operations. The command-line interface (CLI), orchestrated by the run_cli function in strix/interface/cli.py, facilitates penetration tests from the command line. It includes startup displays, configuration of scan parameters, and integration with the telemetry system for real-time status updates. The CLI also handles signal processing for graceful shutdowns. For interactive monitoring, the StrixTUIApp in strix/interface/tui.py offers a Text User Interface (TUI). This interface provides real-time agent monitoring, interactive chat capabilities, dynamic display of statistics, and modal screens for user interactions. The TUI also leverages User Interface Components for Tool Interactions to display tool outputs in a structured and readable format.

The management of sandbox environments, critical for secure tool execution, is handled by the runtime environment components. Specifically, the DockerRuntime class in strix/runtime/docker_runtime.py provisions, initializes, and destroys Docker container-based sandboxes, ensuring isolated and controlled execution of security tools. This is further elaborated in Runtime Environment and Sandboxed Tool Execution. The core application entry point, handled by the main function in strix/interface/main.py, manages the overall lifecycle, including environment validation, Docker image management, argument parsing, and dispatching tasks to either the CLI or TUI.

In multi-agent scenarios, the agents_graph tools in strix/tools/agents_graph enable the creation, communication, and lifecycle management of multiple AI agents. This allows for complex, delegated tasks and provides a hierarchical view of agent interactions, forming a distributed system where agents can collaborate on security assessments. The integration of large language models is managed by a Unified LLM Interaction Interface, ensuring consistent and robust communication with LLMs, which are crucial for the agents' reasoning and decision-making processes.

Base Agent Architecture and Execution Loop
The BaseAgent class, defined in strix/agents/base_agent.py, establishes the core operational framework for all autonomous agents within Strix. It orchestrates the agent's main asynchronous execution loop, manages interactions with Large Language Models (LLMs), processes tool invocations, and handles various execution conditions such as cancellations and errors.

A BaseAgent is initialized with configurations for local sources, non-interactive mode, iteration limits, and LLM settings. It sets up an LLM instance and an AgentState object, which tracks the agent's dynamic information including conversation history, actions, and status. The agent integrates with a global Tracer for logging activities and an agents_graph for inter-agent communication and monitoring. For a detailed description of the agent's state, see Agent State Management and Operational Control.

The agent_loop method is the central asynchronous execution loop. It continuously processes iterations, generating responses from the LLM, executing tools, and managing the agent's state. This loop handles conditions such as reaching maximum iteration limits, LLM failures, and graceful cancellation. It also incorporates mechanisms for the agent to enter a waiting state if input is required or an issue arises, and to resume from such a state.

When an LLM response is received, the agent's _process_iteration method generates a response and logs it. If the LLM output includes tool invocations, the _execute_actions method processes these by creating an asynchronous task to run the specified tools, updating the agent's state with the results. The agent's interactions with LLMs are further detailed in Unified LLM Interaction Interface.

Error handling within the agent_loop is managed by _handle_iteration_error, which catches and logs errors, adding them to the agent's state. The agent can also monitor for new messages from other agents or users through _check_agent_messages, enabling dynamic communication and response within a multi-agent system. This allows for complex workflows where agents can delegate tasks and share information.

Strix Agent for Security Scan Orchestration
The StrixAgent class, defined in strix/agents/StrixAgent/strix_agent.py, extends the BaseAgent and plays a central role in orchestrating security scans. Its initialization process can dynamically configure the underlying Large Language Model (LLM) with specific prompt modules, depending on whether the agent is a top-level agent or a sub-agent within a hierarchical structure.

The core functionality of the StrixAgent is encapsulated in its execute_scan method. This asynchronous method processes a scan_config dictionary, which can contain diverse target types for security assessments. It intelligently parses these targets, which may include code repositories, local code paths, web application URLs, or IP addresses. For local code targets, it constructs specific workspace_path values, suggesting an integration with a structured execution environment. All parsed target information, along with any user-provided instructions, are then consolidated into a comprehensive task_description string. This string serves as the detailed input for the agent's main processing loop, guiding its subsequent actions and leveraging the agent's capabilities to perform the specified security scan. This design allows for flexible and varied security scan definitions, adapting to different testing scenarios and target environments. For more details on the general agent architecture, refer to Base Agent Architecture and Execution Loop.

Command-Line Interface (CLI) Execution
The Strix agent can be run from the command line, orchestrating penetration tests in a non-interactive mode. This process is managed by the run_cli function located in strix/interface/cli.py. This function handles the setup, execution, and reporting of a security scan, providing real-time feedback and detailed summaries upon completion.

During startup, run_cli presents initial information about the penetration test, including scan targets and the designated save location for results. It configures the necessary scan parameters and agent settings, including those for the underlying Large Language Model (LLM) as described in Unified LLM Interaction Interface.

Telemetry integration is a core aspect of CLI execution. A global tracing mechanism, discussed further in Core Tracer Class and Data Collection, is initialized to collect and report scan progress and results. This tracer is configured with a callback function to immediately display any vulnerabilities discovered during the scan to the console.

To ensure robustness, the CLI manages signal handling for graceful shutdowns. This includes registering handlers to perform necessary cleanup operations for the tracer even if the program terminates unexpectedly.

For continuous user feedback, the CLI provides live status updates. A dedicated thread continuously refreshes a live status panel in the terminal, displaying ongoing progress, agent activities, and LLM usage. This allows users to monitor the scan's advancement without interrupting its execution.

The actual security assessment is performed by the StrixAgent, which is instantiated and executed by run_cli. Upon the agent's completion, either successfully or with errors, the CLI displays a final statistics panel and a comprehensive penetration test report, leveraging the collected telemetry data. The process of managing agent operations and their lifecycle is elaborated in Agent Operations and Lifecycle Management.

Multi-Agent Graph Management
The agents_graph tools facilitate the creation, communication, and lifecycle management of multiple AI agents within the Strix framework, enabling complex delegated tasks and providing a hierarchical view of agent interactions. This system allows a root agent to delegate specific tasks to sub-agents, fostering a modular and collaborative approach to security testing.

The system maintains a global, in-memory graph structure that tracks agents as nodes and their communication or delegation relationships as edges. This graph includes metadata for each agent, such as its name, assigned task, current status, and parent agent ID, which establishes a clear hierarchy for delegated responsibilities.

Key functionalities provided by these tools include:

Agent Creation and Execution: A root agent can initiate the creation of new sub-agents, assigning them specific tasks and prompt modules. These sub-agents operate asynchronously in separate threads, each with its own AgentState and StrixAgent instance. The new agent receives its delegated task and context as structured XML, ensuring clear instructions and preventing confusion regarding its role.
Agent Communication: Agents can send messages to specific target agents, enabling the sharing of information, queries, or instructions. This communication is recorded as an "edge" in the agent graph for traceability. Agents can also enter a waiting state, pausing their execution until a message is received from another agent or an external source.
Agent Lifecycle Management: Sub-agents can signal their completion or termination, updating their status in the agent graph and, if necessary, reporting findings or summaries back to their parent agent. The system also supports stopping agents gracefully, updating their status, and ensuring resources are released.
Graph Monitoring: A hierarchical, tree-like view of the agent graph is available, allowing for inspection of agent relationships, tasks, and current statuses. This view includes a summary of all agents' statuses, which helps in understanding the overall progress and state of a multi-agent operation.
This multi-agent graph management system is crucial for orchestrating complex security scans where different aspects of an assessment can be delegated to specialized AI agents, improving the efficiency and comprehensiveness of the testing process. For a more detailed understanding of how individual agents operate, refer to Agent Operations and Lifecycle Management.

Large Language Model (LLM) Integration
The Strix framework integrates Large Language Models (LLMs) to power its autonomous security testing agents. This integration provides a unified interface for various LLM interactions, encompassing configuration management, robust request handling, error management, and efficient context management. It also includes mechanisms for parsing LLM outputs to extract structured tool invocations and tracking usage statistics. Complementing this, Strix manages agent prompt modules, which are specialized Jinja2 templates that inject domain-specific knowledge into agents' system prompts, enabling them to conduct more focused and effective security assessments.

The core of LLM interaction is provided by the LLM class within strix/llm/llm.py, which acts as the primary interface for sending messages to and receiving responses from various LLMs. This class orchestrates the entire LLM interaction lifecycle, including constructing system prompts with dynamic information and tool definitions, and integrating with other components to manage conversational history and parse tool calls from LLM responses. Configuration settings for these interactions, such as the model_name and timeout, are handled by the LLMConfig class defined in strix/llm/config.py, which allows for defaults to be set via environment variables.

To prevent context window overflow and maintain efficient LLM conversations, the framework employs a MemoryCompressor (located in strix/llm/memory_compressor.py). This component intelligently manages conversational history by preserving critical system messages and recent interactions while summarizing older non-system messages using an LLM when token limits are approached. It also handles images in multimodal conversations, prioritizing the most recent ones and replacing older images with textual placeholders to conserve tokens.

Robustness in LLM communication is achieved through the LLMRequestQueue system, implemented in strix/llm/request_queue.py. This system manages concurrent LLM requests, enforcing rate limits and implementing a retry mechanism with exponential backoff for transient errors, thereby ensuring reliable communication with LLM providers. Utility functions in strix/llm/utils.py further support LLM interactions by facilitating the parsing of tool invocations from LLM outputs, formatting tool calls into a structured format, and cleaning content by removing extraneous XML-like tags.

Agent intelligence is augmented by a dynamic system for managing agent prompt modules, found in strix/prompts. These modules are structured knowledge packages, implemented as Jinja2 templates, that contain advanced techniques, practical examples, and validation methods specific to various security domains. The system allows for the discovery, validation, and loading of these modules, categorizing them by vulnerability types, frameworks, technologies, protocols, cloud providers, and reconnaissance techniques. This enables agents to load tailored expertise into their system prompts, enhancing their ability to perform specialized security assessments. For more information on the structure and purpose of these modules, refer to Dynamic Agent Prompt Module Management.

Unified LLM Interaction Interface
The LLM class within strix/llm/llm.py functions as the central point for interacting with various Large Language Models. It manages the lifecycle of LLM calls, from constructing system prompts to processing responses and tracking usage. The class initiates with an LLMConfig instance (defined in strix/llm/config.py), which handles configuration settings such as the model name, prompt caching, and timeouts.

The generate method within the LLM class orchestrates the asynchronous communication with the LLM. It builds a complete message list, beginning with a system prompt dynamically generated using Jinja2 templates, followed by an optional agent identity message, and then the conversational history. To manage context windows effectively, it integrates with the MemoryCompressor (described in Memory Compression and Context Management) to compress older messages. Before sending the request, the LLM class prepares messages for caching, particularly for Anthropic models, to optimize token usage.

Upon receiving a response from the LLM, the LLM class updates usage statistics, including token count and estimated costs, and processes the raw text. This processing involves extracting structured tool invocation details from the LLM's output using parsing utilities. The LLM class also dynamically adjusts request parameters based on the specific model's capabilities, such as incorporating stop sequences or reasoning_effort when supported, and filters out image content if the target model does not support vision capabilities. Error handling is also centralized, catching exceptions from the underlying litellm library and re-raising them as LLMRequestFailedError for consistent error management.

For managing concurrent requests and adhering to rate limits, the LLM class leverages a global request queue. This queue, provided by get_global_queue in strix/llm/request_queue.py, ensures reliable communication with LLM providers by implementing retry logic with exponential backoff for transient errors, as detailed in Robust LLM Request Queuing and Retry Mechanisms.

Memory Compression and Context Management
The MemoryCompressor class, defined in strix/llm/memory_compressor.py, manages conversational history to prevent Large Language Model (LLM) context window overflow. This system prioritizes the preservation of critical messages while summarizing older, less immediate content, and handles image limits to optimize token usage.

The compression strategy involves several steps:

Image Management: The system limits the number of images in the conversation, prioritizing more recent ones and replacing older images with a textual placeholder if a predefined maximum is exceeded.
System Message Preservation: All messages categorized with a "system" role are always retained, ensuring that core operational context and instructions are never lost.
Recent Message Preservation: A minimum number of the most recent non-system messages are preserved intact, maintaining immediate conversational flow.
Summarization: If the total token count approaches the LLM's context window limit, older non-system messages are summarized in chunks. This summarization is performed by an LLM itself, which condenses the content based on a detailed prompt template designed to retain critical security assessment information. If summarization fails, a graceful fallback mechanism ensures that the first message of the chunk is returned, preventing loss of context.
Token counting is performed using litellm.token_counter for accuracy, with a fallback to a character-based estimate if necessary. This ensures efficient management of the LLM's context window.

Robust LLM Request Queuing and Retry Mechanisms
The LLMRequestQueue system manages concurrent requests to large language models, enforcing rate limits and ensuring reliable communication with LLM providers through robust retry mechanisms. This system prevents overloading LLM services and handles transient network issues or service unavailability gracefully.

At its core, the LLMRequestQueue class manages the flow of LLM requests. It uses a bounded semaphore to limit the number of simultaneous requests, ensuring that the application does not exceed the LLM provider's concurrency limits. Additionally, a delay mechanism is in place to control the rate at which requests are sent, adhering to specified rate limits. These parameters can be configured through environment variables, providing flexibility in deployment.

To enhance reliability, the system incorporates a retry mechanism with exponential backoff. If an LLM request fails due to a transient error, the system automatically retries the request after increasing delays. The decision to retry an exception is based on whether the error's status code indicates a temporary issue. This logic, leveraging the tenacity library, ensures that intermittent failures do not disrupt the application's operation.

A global instance of the LLMRequestQueue is maintained, simplifying its use across different parts of the application and ensuring consistent management of all LLM interactions. For further details on LLM integration, refer to Unified LLM Interaction Interface.

LLM Output Parsing and Tool Invocation
Utility functions manage the parsing, formatting, and cleaning of structured output from Large Language Models (LLMs), particularly for handling tool invocations. These functions are central to how agents interact with external capabilities by interpreting LLM-generated instructions and presenting clean responses.

The parse_tool_invocations function in strix/llm/utils.py is responsible for extracting tool names and their arguments from an LLM's raw text output. LLMs often embed structured calls to tools within their responses, which this function processes to identify the specific tool to be invoked and the parameters required for its execution. It also handles HTML unescaping for argument values, anticipating that LLMs might produce HTML-encoded characters in their output.

Conversely, the format_tool_call function in strix/llm/utils.py constructs the XML-like string representation of a tool call. This function takes a tool's name and its arguments and generates the formatted string that the LLM is designed to understand and reproduce.

The clean_content function, also in strix/llm/utils.py, removes tool invocation blocks and other specified XML-like tags (such as inter_agent_message and agent_completion_report) from the LLM's content. This ensures that only the relevant, non-tool-related text is presented, preventing extraneous information from cluttering agent communication or final outputs. Additionally, an internal helper function, _truncate_to_first_function, helps manage scenarios where an LLM might attempt to invoke multiple tools in a single turn by truncating the content to the first tool function tag. Another utility, _fix_stopword, corrects malformed closing tags for tool invocations, addressing common LLM output inconsistencies.

These utilities facilitate agent interaction by providing a standardized way to interpret and generate tool-related instructions, ensuring a clear interface between the LLM's natural language generation and the structured execution of external tools. The LLM integration is further detailed in Unified LLM Interaction Interface.

Dynamic Agent Prompt Module Management
The management of agent prompt modules enables Strix agents to dynamically load specialized knowledge tailored for specific security testing scenarios. These modules are Jinja2 templates, structured to provide advanced techniques, practical examples (payloads, commands), and validation methods. By injecting these modules into an agent's system prompt during creation, the agent gains tailored expertise for a given task, augmenting its baseline security knowledge. Agents can utilize up to five such modules, which are organized into categories like /vulnerabilities, /frameworks, /technologies, /protocols, /cloud, /reconnaissance, and /custom as detailed in strix/prompts/README.md.

The system facilitates the discovery of available prompt modules, validation of requested module names, and generation of human-readable descriptions for these modules. The load_prompt_modules function in strix/prompts/__init__.py is central to loading the content of specified prompt modules. It processes a list of module names and a Jinja2 environment to render the templates, handling various path formats (simple names or categorical paths). This dynamic loading mechanism ensures that Strix agents can adapt their expertise based on the security domain or technology stack under assessment.

Runtime Environment and Sandboxed Tool Execution
The Strix framework manages isolated runtime environments, primarily Docker container-based sandboxes, to execute security tools securely and controllably. This mechanism allows agents to perform security assessments without direct access to the host system, ensuring that potentially risky operations are confined. The system provisions and destroys these sandboxes as needed, executing tools within these environments through a defined interface.

The core of this system is an abstract interface for sandbox management, defined by the AbstractRuntime base class in strix/runtime/runtime.py. This class establishes a contract for any runtime implementation, outlining methods for provisioning new sandboxes (create_sandbox), obtaining access URLs (get_sandbox_url), and destroying sandboxes (destroy_sandbox). The information returned upon sandbox creation is standardized through the SandboxInfo TypedDict, which includes details such as workspace_id, api_url, and auth_token.

The concrete implementation, DockerRuntime, found in strix/runtime/docker_runtime.py, manages these isolated execution environments using Docker containers. It handles the full lifecycle of a container, from initial provisioning and setup to its eventual destruction. This involves generating unique scan IDs, managing Docker images (defaulting to ghcr.io/usestrix/strix-sandbox:0.1.10), and dynamically allocating network ports for internal services like the Caido proxy and a tool server. The _get_or_create_scan_container method optimizes this process by reusing existing containers when possible, reducing overhead. Once a container is created, _initialize_container sets up necessary services within it, such as starting the Caido proxy and the tool_server.py application. Local source directories can also be copied into the container to enable scans of specific codebases.

Within each sandbox, a FastAPI server, implemented in strix/runtime/tool_server.py, runs to facilitate secure tool execution. This server acts as an intermediary, processing requests from agents to execute tools within the isolated environment. It enforces sandboxing by requiring the STRIX_SANDBOX_MODE environment variable to be set, and uses Bearer token authentication to ensure only authorized requests are processed. Tool execution for each agent is isolated in its own dedicated child process, managed by ensure_agent_process, which uses inter-process communication queues to handle requests and responses. This design ensures that tools run securely and independently, preventing resource conflicts or security breaches between different agents.

The sandbox containers themselves are built using a Dockerfile located in containers/Dockerfile. This Dockerfile creates a comprehensive Kali Linux-based environment, installing a wide array of security tools, development kits (Python, Go, Node.js), and configuring a non-root pentester user. It also generates and installs a self-signed Root CA certificate for SSL/TLS interception, which is essential for analyzing encrypted traffic during security assessments. Abstract Runtime Interface and Implementation
The Strix framework defines an abstract interface for managing sandboxed environments, which isolates the execution of security tools and agent operations. This interface is encapsulated by the AbstractRuntime base class within strix/runtime/runtime.py. This class establishes a contract for any runtime that provisions, interacts with, and destroys sandboxes, ensuring a consistent API regardless of the underlying containerization technology. The primary methods defined in AbstractRuntime include create_sandbox for provisioning a new isolated environment, get_sandbox_url for retrieving access details to services within the sandbox, and destroy_sandbox for terminating and cleaning up the environment.

A concrete implementation of this abstract interface is provided by the DockerRuntime class, found in strix/runtime/docker_runtime.py. This implementation leverages Docker containers to create and manage sandboxes. When a sandbox is created via DockerRuntime, it returns a SandboxInfo object, a TypedDict that contains essential details such as the workspace_id, the API URL for internal services, an authentication token, the tool server port, and the agent's identifier. The get_runtime function in strix/runtime/__init__.py acts as a factory, providing the appropriate runtime instance based on configuration, currently supporting only the Docker-based implementation. This design allows Strix to maintain a clear separation between the abstract definition of runtime behavior and its specific implementation using Docker, making it extensible for other containerization technologies in the future. For more details on the specific mechanisms of Docker-based sandbox management, refer to Docker-based Sandbox Provisioning and Lifecycle.

Docker-based Sandbox Provisioning and Lifecycle
The DockerRuntime class in strix/runtime/docker_runtime.py implements the AbstractRuntime interface to manage sandboxed environments using Docker containers. This enables secure and isolated execution of security scanning tools.

The process of creating a sandbox begins by generating a unique scan identifier. The runtime then attempts to reuse an existing Docker container associated with this identifier. If no suitable container is found, a new one is provisioned. This involves pulling the strix-sandbox Docker image (defaulting to "ghcr.io/usestrix/strix-sandbox:0.1.10"), dynamically allocating available ports for the Caido proxy and an internal tool server, and running the container with specific capabilities and environment variables. Once the container is started, internal services are initialized. This setup includes starting the Caido proxy and a FastAPI tool server within the container. If local source files are provided, they are copied into the container's /workspace directory, ensuring they are accessible within the sandboxed environment. Finally, the agent is registered with the tool server running inside the sandbox.

For more details on the abstract interface, see Abstract Runtime Interface and Implementation. The tool server, running within the sandbox, is further described in Sandboxed Tool Server and Secure Execution.

When a sandbox is no longer needed, the destroy_sandbox method stops and removes the associated Docker container, cleaning up the environment. The DockerRuntime also handles resolving accessible URLs for services running within the container, taking into account the Docker host environment.

Sandboxed Tool Server and Secure Execution
A FastAPI server, defined in strix/runtime/tool_server.py, operates within each Docker sandbox to facilitate secure and controlled execution of tools by Strix agents. This server acts as the primary interface for agents to invoke tools, ensuring that all tool interactions remain isolated within their respective sandboxes. Its design emphasizes security, process isolation, and authenticated access.

Upon sandbox creation, the FastAPI server is initialized and configured to run within the container, providing endpoints for tool execution requests. A critical security measure is the explicit check for STRIX_SANDBOX_MODE="true" environment variable, ensuring the server only operates in a designated secure environment. All requests to the server, with the exception of health checks, require Bearer token authentication, which is verified against a pre-configured EXPECTED_TOKEN. This prevents unauthorized access to the sandbox's tool execution capabilities.

The server manages dedicated child processes for each agent that interacts with it. When an agent sends a tool execution request, the ensure_agent_process function creates or identifies a specific process for that agent_id. This isolation prevents resource conflicts and enhances security by ensuring that one agent's actions do not interfere with another's. Tool execution requests are passed to these child processes via inter-process communication queues, and responses (results or errors) are returned through a separate response queue. This architecture leverages Python's multiprocessing module to achieve parallel and isolated execution. The agent_worker function within these child processes handles the actual tool invocation, argument conversion, and result formatting.

Additionally, the server incorporates robust cleanup mechanisms. Signal handlers for SIGTERM and SIGINT ensure that all active agent processes are gracefully terminated when the server shuts down, preventing orphaned processes and resource leaks. This is managed by the cleanup_all_agents function, which systematically signals each agent process to shut down and then ensures their termination.

Comprehensive Browser Automation
Browser automation within Strix is facilitated by a multi-layered architecture that enables agents to interact with web pages. The browser_action function, defined in strix/tools/browser/browser_actions.py, serves as the primary interface for triggering various browser operations. This function dispatches requests to a BrowserTabManager, which orchestrates interactions and manages the browser's state.

The BrowserTabManager, implemented in strix/tools/browser/tab_manager.py, functions as a singleton to ensure a single, consistent point of control over the browser instance. It handles tasks such as launching and closing the browser, navigating to URLs, managing tabs (e.g., creating new tabs, switching between them), and performing user-like interactions such as clicks, text input, and scrolling. The manager also supports advanced capabilities like executing JavaScript within the page context and retrieving console logs or page source. It employs a threading lock to ensure thread-safe operations, preventing race conditions when multiple parts of the system might attempt to interact with the browser simultaneously. Additionally, the BrowserTabManager includes cleanup handlers to ensure graceful shutdown of the browser instance, even in the event of unexpected program termination.

Underneath the BrowserTabManager is the BrowserInstance class, found in strix/tools/browser/browser_instance.py. This class directly manages the Playwright browser environment. Playwright is an asynchronous automation library, but BrowserInstance provides a synchronous interface to its functionalities. This is achieved by running an asyncio event loop in a separate thread and exposing synchronous methods that schedule and await asynchronous Playwright tasks on that loop. This design allows other components of Strix, which might operate synchronously, to seamlessly interact with the browser. BrowserInstance handles the full lifecycle of the browser, from launching a headless Chromium instance to managing its context and pages. It incorporates mechanisms for capturing page state, including screenshots and tab information, and manages console logging with truncation to prevent excessive output. Error handling is integrated throughout, ensuring robust operation and informative feedback when issues arise during browser interactions.

These renderers, all inheriting from the BaseToolRenderer defined in strix/interface/tool_components/base_renderer.py, are designed to provide consistent formatting, styling, and content truncation across diverse tool types. The BaseToolRenderer provides common functionalities such as escape_markup for sanitizing text, format_args and format_result for consistent data presentation, get_status_icon for visual status indicators, and get_css_classes for dynamic styling.

Each specialized renderer is associated with a particular tool via the @register_tool_renderer decorator, which integrates it into the ToolTUIRegistry described in Tool TUI Registry for Discoverability and Dispatch. This mechanism enables the system to dynamically select the appropriate renderer based on the tool being executed.

For agent-related orchestrations, renderers such as CreateAgentRenderer and AgentFinishRenderer from strix/interface/tool_components/agents_graph_renderer.py display information about agent creation, message passing, and completion status. Similarly, strix/interface/tool_components/browser_renderer.py's BrowserRenderer handles browser automation actions, formatting URLs, text, and JavaScript code. For file system operations, StrReplaceEditorRenderer, ListFilesRenderer, and SearchFilesRenderer in strix/interface/tool_components/file_edit_renderer.py provide visual feedback for file modifications, listings, and searches.

Syntax highlighting is a key feature, particularly for code and command outputs. The BrowserRenderer in strix/interface/tool_components/browser_renderer.py and PythonRenderer in strix/interface/tool_components/python_renderer.py utilize the pygments library for robust syntax highlighting of JavaScript and Python code, respectively. The TerminalRenderer in strix/interface/tool_components/terminal_renderer.py extends this to bash commands, providing color-coded output that enhances readability. These renderers employ utility methods like _get_style_colors (often cached for performance) and _get_token_color to map pygments token types to appropriate colors for Textual's rich text markup.

Additional specialized renderers cover a wide range of functionalities:

strix/interface/tool_components/notes_renderer.py contains renderers like CreateNoteRenderer and ListNotesRenderer for managing in-memory notes.
strix/interface/tool_components/proxy_renderer.py offers renderers such as ListRequestsRenderer and SendRequestRenderer for interacting with network proxies.
strix/interface/tool_components/reporting_renderer.py includes CreateVulnerabilityReportRenderer for displaying vulnerability details with color-coded severity.
strix/interface/tool_components/scan_info_renderer.py provides ScanStartInfoRenderer and SubagentStartInfoRenderer for initial scan and subagent information.
strix/interface/tool_components/thinking_renderer.py's ThinkRenderer visually represents the AI's thought processes.
strix/interface/tool_components/user_message_renderer.py's UserMessageRenderer formats messages from the user.
strix/interface/tool_components/web_search_renderer.py's WebSearchRenderer displays web search queries and results.
strix/interface/tool_components/finish_renderer.py's FinishScanRenderer communicates the conclusion of a scan operation.
Content truncation is consistently applied across renderers, for example, in _format_url and _format_text within strix/interface/tool_components/browser_renderer.py, to prevent overly long outputs from disrupting the UI layout while still conveying essential information. This unified approach ensures that all tool interactions are presented clearly and consistently within the Textual user interface.
